# NetPulse — Features Nuevos y Arquitectura (2026-08-11)

## Estructura del backend (mejorada)

```
app/
├── core/           # settings (config centralizada), security (JWT), limiter
├── middleware/     # auth (JWT + API keys), rbac, security headers, audit, metrics
├── models/         # schemas Pydantic
├── routers/        # endpoints HTTP (18 routers)
├── services/
│   ├── collectors/     # syslog_svc (UDP→Loki), snmp_svc (polling SNMP)
│   ├── notify/         # telegram.py, email_smtp.py (canales de alerta)
│   ├── ops/            # maintenance, drift, config_versions, health, capacity, backup_netpulse
│   ├── security/       # totp_svc (2FA), api_keys_svc (API keys)
│   ├── integrations/   # loki_proxy (log viewer), netbox_sync (fuente de verdad)
│   └── reports/        # csv_report (inventario, health)
└── utils/          # errores
```

## Features implementados

### 1. Syslog collector → Loki
- Servidor UDP en 0.0.0.0:5514 (514 requiere root; configurable con NETPULSE_SYSLOG_PORT)
- Arranca automáticamente con la API (NETPULSE_SYSLOG_ENABLED=true)
- Parsea RFC3164 (facility, severity, host, mensaje) y empuja a Loki
- Endpoints: GET /api/collectors/syslog/status, POST /start, POST /stop

### 2. SNMP polling
- Polling de CPU/mem/uptime vía pysnmp (fallback a snmpget CLI)
- Endpoints: POST /api/collectors/snmp/poll, GET /api/collectors/snmp/poll/{device_id}

### 3. Topología LLDP
- GET /api/topology/map — nodos + enlaces desde LLDP de todos los dispositivos
- GET /api/topology/interfaces/{device_id} — interfaces con estado

### 4. Tráfico por interfaz
- GET /api/traffic/interfaces/{device_id}?range_hours=N — series RX + interfaces
- GET /api/traffic/summary

### 5. Canales de alerta (Telegram / Email)
- notify/telegram.py: send_telegram(bot_token, chat_id, message)
- notify/email_smtp.py: send_email_smtp (STARTTLS) y send_email_plain
- Config: NETPULSE_TELEGRAM_TOKEN/CHAT_ID, NETPULSE_SMTP_*
- El webhook de Alertmanager reenvía a Telegram/Email si están configurados

### 6. Ventanas de mantenimiento
- CRUD en config/maintenance_windows.json
- El webhook de alertas SUPRIME alertas de dispositivos en mantenimiento
- Endpoints: GET/POST /api/ops/maintenance, GET /active, DELETE /{id}

### 7. Drift detection
- Compara running-config vs baseline (config/baselines/<device>.cfg)
- Guarda configs con drift en config/drift_history/
- Endpoints: GET /api/ops/drift/{device_id}, POST /api/ops/drift/check-all

### 8. Versiones de config
- Indexa backups/*.cfg con sha256 y timestamp
- Diff entre dos versiones (difflib)
- Endpoints: GET /api/ops/config-versions, GET /{device}/{filename}, GET /diff/{device}

### 9. Log viewer (Loki proxy)
- GET /api/logs/query?query=...&hours=N&limit=N — consulta logs en Loki
- GET /api/logs/labels — labels conocidas
- Sin Grafana: el dashboard consulta Loki vía este proxy

### 10. Health score por dispositivo
- Score 0-100: CPU>70%, RAM>80%, disco>85% penalizan
- Endpoints: GET /api/ops/health/{device_id}, GET /api/ops/health/all

### 11. Reportes CSV
- GET /api/reports/inventory.csv — inventario completo
- GET /api/reports/health.csv — health scores

### 12. Capacity planning
- GET /api/ops/capacity/{device_id}?days=90 — proyección lineal desde Prometheus

### 13. 2FA / TOTP
- RFC6238 (HMAC-SHA1, 30s, 6 dígitos) — implementación propia sin pyotp
- POST /api/security/2fa/setup — genera secreto + data URI QR
- POST /api/security/2fa/verify — valida código

### 14. API keys
- Keys np_<hex> almacenadas SOLO como hash sha256
- La autenticación JWTBearer acepta np_... como Bearer
- Endpoints: GET/POST /api/security/api-keys, DELETE /{id}

### 15. Backup de NetPulse
- POST /api/ops/backup — empaqueta config (devices.yaml, users, webhooks, jobs, keys)
- Excluye secretos (.fernet_key, .netbox_token)
- Output: backups/netpulse_self_<timestamp>.tar.gz

### 16. NetBox como fuente de verdad
- GET /api/netbox/devices — lista desde NetBox API
- POST /api/netbox/sync — sincroniza a inventario local (driver ios por defecto)

## Dashboard (nuevas vistas)
- 🗺️ Topology — nodos + enlaces LLDP

# 🗺️ 2026 — Topología como Mapa + Traceroute geolocalizado

La vista **Topología** ahora tiene 3 modos (tabs): 🕸️ Grafo, 🌍 Mapa, 📋 Tabla.

## Grafo interactivo (canvas)
- Nodos LLDP dibujados con simulación de física (repulsión + resortes).
- Arrastrar nodos, zoom con rueda (doble click resetea pan/zoom), hover muestra
  tooltip con driver/group/IP/puertos del enlace y resalta enlaces vecinos.
- Vecinos LLDP fuera del inventario aparecen como nodos "fantasma" (grises).

## Mapa geográfico (Leaflet vendoreado)
- Leaflet 1.9.4 servido desde `static/vendor/` (sin CDN externa para el JS/CSS;
  los tiles se descargan de OpenStreetMap en runtime).
- Coloca la base **GeoLite2-City.mmdb** de MaxMind en `config/GeoLite2-City.mmdb`
  (o `NETPULSE_GEOIP_DB=/ruta/mmdb`) para activar geolocalización de equipos
  públicos y saltos de traceroute. Sin base: `geo=None` y el mapa funciona igual
  (traceroute se lista, solo sin geolocalización ni línea entre saltos).

## Traceroute interactivo
- `POST /api/topology/traceroute` `{origin, destination}`:
  - `origin`: `"noc"` (el servidor NetPulse ejecuta `traceroute`/`tracert` en OS)
    o `device_id` (ejecuta `traceroute <dest>` en el CLI vía NAPALM; drivers
    ios/eos/junos/nxos/iosxr/ros). Requiere rol `operator+`; audita la ejecución.
  - Valida el destino con regex (bloquea shell injection), parsea saltos
    multi-vendor y geolocaliza cada IP con GeoIP.
  - Cada salto que coincide con un `hostname`/IP del inventario se marca.
- UI: origen (Servidor NetPulse / equipos), destino, botón Ejecutar; los saltos
  se dibujan en el mapa (polyline punteada + popups salto/host/RTT/ciudad) con
  tabla salto-por-salto debajo.

# 🧪 Laboratorio Docker (lab-net / core / access / dmz)

`docker-compose.lab.yml` crea 4 redes segmentadas para que el **grafo de
topología dibuje enlaces reales entre algunos equipos y no entre otros**:

```
lab-net    172.30.0.0/24 (gestión: cisco/juniper/switch)
core-net   172.30.1.0/24 (cisco+juniper)
access-net 172.30.2.0/24 (cisco+switch)
dmz-net    172.30.3.0/24 (juniper+mikrotik)
```

Malla LLDP esperada (verificada): `cisco↔switch` (access), `cisco↔juniper`
(core), `juniper↔mikrotik` (dmz). **Arista** (`arista-core-01`) no arranca en
Apple Silicon (perfil `arista` desactivado) y aparece aislada.

## Quirks del kernel/firewall que el mapa exige (⚠)

Linux no reenvía *frames link-local* (LLDP, ether 0x88cc) por un bridge sin el
bit 14 de `group_fwd_mask`. El script **`scripts/lab-net-lldp.sh`** lo aplica
(idempotente) a:

- Todos los bridges de Docker de redes `netpulse-noc_*` (lab-net con `0x0`
  para FILTRAR la intranet de gestión; el resto `0x4000`).
- `qemubr1` interno del contenedor RouterOS (lo aplica su propio
  `docker/routeros/rootfs/qemu-ifup`, ver abajo).
- nat/PREROUTING + filter/FORWARD `ACCEPT 172.30.0.0/16`: Docker Desktop
  inserta `DROP` anti-spoofing en PREROUTING por cada puerto publicado
  (rompe traceroute/ping inter-red del lab en la propia VM). Sin ese accept,
  los equipos no se alcanzan entre segmentos aunque el LLDP funcione.

## LLDP dentro de los contenedores FRR

- `lldpd` corre en cisco/juniper/switch (FRR no habla LLDP). El socket de
  control `/run/lldp/lldpd.socket` es del grupo `lldpd` (770): el usuario SSH
  `admin` debe pertenecer a ese grupo para que el fallback `llpdcli show
  neighbors` de `napalm_svc.get_lldp_neighbors` funcione (lo hace
  `docker/frr/Dockerfile` + `frr-entrypoint.sh`).
- **No usar** `-I` de lldpd (en Alpine 1.0.14 cualquier patrón deja 0
  interfaces anunciables) ni iptables dentro de los contenedores (la VM de
  Docker Desktop no tiene los módulos).

## MikroTik (RouterOS emulado — `vaerh/routeros`)

- La imagen crea **una sola NIC qemu** (`-nic tap`, bridge `qemubr1` interno):
  el RouterOS vive **solo en dmz-net** (172.30.3.13 por el udhcpd del
  contenedor). ether2 nunca existirá con esta imagen.
- **Disco persistente**: `./docker/routeros/rootfs/` se monta en `/routeros`
  (vdi + scripts del entrypoint). La configuración (API 8728, ssh, identity)
  sobrevive recreaciones. Reset de fábrica = borrar `rootfs/` y volver a
  extraerla: `docker create tmp vaerh/routeros && docker cp tmp:/routeros/. docker/routeros/rootfs/`.
- Config mínima aplicada (queda en el disco): `ip service enable api`,
  `ip service enable ssh`, `system identity set name=mikrotik-edge-01`
  (el mapa usa el SysName LLDP para casar el nodo del inventario),
  `interface list add name=lab; interface list member add list=lab
  interface=ether1; ip neighbor discovery-settings set
  discover-interface-list=lab` (LLDP discovery sale por la lista vacía
  "static" por defecto → sin vecinos).
- Conexión: SSH puerto publicado 2225 (`admin`, sin password; el cliente
  **OpenSSH funciona con ROS**, paramiko NO), API 8728 (librouteros), Winbox
  8291 console-over-attach es frágil bajo emulación TCG.

## Traceroute en el lab

- `origin=noc` → 8.8.8.8 funciona (server `traceroute` real).
- `origin=<device>` → los FRR hacen fallback `tracepath`; en el lab se alcanza
  el destino **mismo segmento** (ej. juniper→mikrotik) y público si hay
  default gw; inter-segmento depende de las reglas `ACCEPT 172.30/16` del
  script. RouterOS: solo responde por su camino actual (1 hop L2 adyacente).
- GeoIP: sin base GeoLite2 los saltos salen `geo=null` (el código soporta
  fallback online por env, ver `app/services/geoip_svc.py`).
